## Suggested title

`CPUSolver` converges (in ~30 iters) to non-physical k_eff under specific 2-group pin-cell configurations

## Body

### Summary

OpenMOC's `CPUSolver` declares `converged=true` after ~30 power-iteration
sweeps and reports a stable but non-physical k_eff under two reproducible
2-group pin-cell configurations on the `3D-MOC` branch. OpenMC running
the same multigroup case (same cross sections, same geometry, same
boundary conditions) produces a physically reasonable k_eff that
disagrees with OpenMOC by 30–50%. Tightening
`convergence_threshold` from `1e-4` down to `1e-7` does not resolve
the issue, so this is not a "needs more iterations" case but a
power-iteration **basin-of-attraction** problem: the iteration is
genuinely fixed-point-stable on the wrong eigenvalue.

### Reproduction

Clone OpenMOC (`mit-crpg/OpenMOC` branch `3D-MOC`, commit pinned at
the time of MetBench Stage 5 Phase 2). Build the SWIG `_openmoc.so`
extension (the upstream Dockerfile recipe works).

The two reproducers below use a 2-group reflective pin-cell with
fuel cylinder + moderator. Identical OpenMC inputs ship with the
MetBench repository (`SUT/openmc/openmc_runner.py`) for cross-check.

#### Configuration A — high moderator absorption

```python
import openmoc

# Materials (2 group, MetBench reference)
fuel = openmoc.Material(name="fuel")
fuel.setNumEnergyGroups(2)
fuel.setSigmaT([0.222222, 0.833333])
fuel.setSigmaS([0.192423, 0.020000, 0.000000, 0.753300])
fuel.setNuSigmaF([0.006400, 0.156500])
fuel.setSigmaF([0.002500, 0.066600])
fuel.setChi([1.0, 0.0])

mod = openmoc.Material(name="moderator")
mod.setNumEnergyGroups(2)
# baseline mod sigma_t = [0.230, 1.530], sigma_a = [0.0004, 0.020]
# follow-up: scale moderator sigma_a by 1.5; recompute sigma_t to match
mod.setSigmaT([0.2302, 1.540])  # = baseline + (1.5-1)*sigma_a
mod.setSigmaS([0.219000, 0.010600, 0.000000, 1.510000])
mod.setNuSigmaF([0.0, 0.0])
mod.setSigmaF([0.0, 0.0])
mod.setChi([0.0, 0.0])

# 1.26 cm × 1.26 cm × 1.0 cm reflective pin cell, fuel radius 0.4 cm
# ... (full geometry omitted; standard reflective ZCylinder in a box)

solver = openmoc.CPUSolver(track_generator)
solver.setConvergenceThreshold(1e-7)
solver.computeEigenvalue(1000)
print(solver.getKeff(), solver.getNumIterations())
# observed: 0.4764 30  (basin pathology)
# expected: ~0.97       (OpenMC multi-group on the same JSON gives 0.9683 ± 0.0017)
```

A factor sweep on the moderator sigma_a multiplier shows the
discontinuity:

| factor | OpenMOC k_eff | iters |
|-------:|--------------:|------:|
| 1.01 | 1.12935 | 552 |
| 1.05 | 1.11476 | 548 |
| 1.10 | 1.09710 | 544 |
| 1.20 | 1.06352 | 535 |
| **1.50** | **0.47635** | **30** |

The k_eff drop between factor=1.20 and factor=1.50 is mathematically
implausible (~50 percentage points for a small cross-section change);
the iteration count cliff (535 → 30) is the visible signature.

#### Configuration B — off-centre fuel at extent 1.50 cm

Same materials as Configuration A but unmodified moderator
(factor=1.0). Geometry: 1.50 × 1.50 × 1.0 cm reflective pin cell,
fuel ZCylinder centred at (+0.15, -0.10) cm, radius 0.4 cm.

OpenMOC: k=0.5356, 35 iters.
OpenMC same input: k=0.9594 ± 0.0019.

Reducing the cell extent to 1.30 cm (with offset (+0.10, -0.08))
lands back in a well-converged basin (k=1.103, 558 iters). The bad
basin is narrow but reproducible.

#### Cross-check: tightening `convergence_threshold` does not help

```python
solver.setConvergenceThreshold(1e-7)   # was 1e-4 default
solver.computeEigenvalue(5000)
# Configuration A still returns k=0.4764 in 30 iters.
```

So this is **not** "the iteration would have left the basin with more
iterations"; it's a stable wrong fixed point of the unaccelerated
power iteration on this material.

### Suspected root cause

Unaccelerated power iteration on a problem whose dominant and
sub-dominant eigenvalues are close (or whose eigenvector basis has
near-degenerate components on the source distribution generated by
OpenMOC's flat-source-region initial guess) can converge to a
non-physical eigenvalue that is locally stable. A Wielandt shift,
Anderson acceleration, or Chebyshev acceleration would typically
escape this basin. We have not patched OpenMOC to verify but the
literature on power-iteration acceleration in MOC codes (e.g.
Boyd et al., MOC method-of-characteristics review papers) is
consistent with this hypothesis.

### Why this matters

The user (a downstream tool) has no easy way to know that
`converged=true` from `CPUSolver` is suspect. The reported k_eff is
internally consistent (subsequent iterations don't move) and the
runtime drops noticeably (30 iters vs 500+), but neither of those
signals is currently exposed as a warning.

### Suggested mitigations (in order of effort)

1. **Cheapest**: emit a warning when `getNumIterations() < 50`, since
   genuinely-converged eigenvalue problems on this material class
   take ≥500 iterations. (False positive rate would need
   characterisation, but a simple "early-converge suspicious"
   warning would already help downstream users.)
2. **Medium**: implement Wielandt shift in `CPUSolver`. Existing
   literature shows this stabilises power iteration against
   near-degenerate eigenvalue spectra without rewriting the solver.
3. **More invasive**: switch the default to Anderson acceleration
   with the existing eigenvalue solver as a fallback.

### Discovery context

This was discovered by [MetBench](link), a metamorphic-testing
benchmark suite that runs cross-program comparisons (OpenMOC vs
OpenMC on identical multigroup inputs). The full discussion lives
in `docs/experiments/historical-bugs.md` (Case 4) and
`docs/experiments/discussion-phase2.md` (the "OpenMOC convergence
pathology" section).

We have **not** filed this as a blocker because (a) the bad basins
are narrow enough that typical user inputs avoid them, and (b)
working around them in a downstream tool is straightforward (we
just steer our test cases away from the affected configurations).
But documenting the pathology upstream feels appropriate.
