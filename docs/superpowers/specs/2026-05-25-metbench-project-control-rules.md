# MetBench 项目控制规则

> **日期**: 2026-05-25  
> **状态**: 生效  
> **目的**: 防止项目失控、失速、失真。把监控、开发、验收、文档、双环境验证统一到一套可执行规则上。  
> **适用范围**: MetBench 仓库 `main` 主线、所有 feature branch、Windows VM 验证、Cloud 端实现与测试。

---

## 1. 控制目标

本规则只追求三件事：

1. **不失控**：任何人都能回答“当前主线做到哪了、下一步做什么、谁能改什么”。
2. **不失速**：开发不在旧认知、旧计划、旧分母上反复返工。
3. **不失真**：代码、文档、监控、GitHub 状态表达的是同一件事。

---

## 2. 单一事实源层级

MetBench 的正式判断必须按下面顺序取证，低层不能推翻高层。

### 2.1 一级事实源：主线状态

- `origin/main` 当前提交号
- GitHub 已合并 PR 链
- 根工作区是否与 `origin/main` 同步

**硬规则**：

- 任何“当前项目状态”表述，必须先给出当前主线提交号。
- 本地开发 worktree、未推送分支、临时测试回执，**不得**冒充仓库状态。

### 2.2 二级事实源：四份核心文档

仅以下四份文档可作为“完成度 / 路线图 / 基线 / 结构”正式口径：

- `AGENTS.md`
- `CLAUDE.md`
- `docs/requirements.md`
- `docs/PROJECT-STRUCTURE.md`

**硬规则**：

- 这四份文档之间如果冲突，以“冲突”本身视为阻塞问题，必须先修。
- 任何 plan/spec/report 都不能在未同步这四份文档时宣称“主线已完成”。

### 2.3 三级事实源：测试与验收证据

按下面顺序使用：

1. 最近可审计精确绿基线（提交号 + pass/fail/skip）
2. 对应测试工件（TRX、切片测试、CI 记录）
3. Windows 构建与 UI 回执

**硬规则**：

- 文档-only PR 不刷新代码测试绿基线。
- Cloud 测试基线与 Windows 回执分开记录，禁止混成一条“已验证”。

### 2.4 四级事实源：计划与设计文档

`docs/superpowers/plans/*.md` 与 `docs/superpowers/specs/*.md` 默认分两类：

- **活跃文档**：当前仍指导主线开发
- **历史文档**：记录既往阶段，不再作为当前执行口径

**硬规则**：

- 任何计划文档如果引用的主线提交号、分母、阶段状态落后于四份核心文档，则自动降级为“历史文档”。
- 监控与执行不得从历史计划文档中直接提取当前状态。

---

## 3. 活跃计划注册制度

### 3.1 每个阶段只能有一份主计划

每个活跃开发阶段只能有：

- 1 份主计划（master plan）
- 0 到 N 份子计划（sub-plans）

但必须明确：

- 哪份是当前主计划
- 哪些子计划仍有效
- 哪些只保留历史记录

### 3.2 活跃计划最低要求

任何活跃计划必须同时满足：

1. 写明对应主线提交基线
2. 写明前置条件
3. 写明验收标准
4. 写明测试命令或回执类型
5. 写明 Cloud / Windows 分工
6. 写明不在本轮范围内的内容

缺少其中任意一项，不得作为执行依据。

---

## 4. 开发闸门

### 4.1 编程前置闸门

开始任何实现前，必须先满足：

1. 功能已登记到 `docs/requirements.md`
2. 有明确 spec 或设计说明
3. 有当前活跃计划
4. 已识别高风险歧义
5. 已定义验收标准

**禁止**：

- 边写边定核心语义
- 在多个共享边界上并行改动
- 未消除歧义就开始编码

### 4.2 PR 闸门

每个 PR 必须小、短、单目标。

每个 PR 必须包含：

- 改动目标
- 作用边界
- 测试证据
- review 结论
- 是否影响四份核心事实源

**禁止**：

- 功能实现 + 状态修正 + 架构改写混在一个大 PR
- 没有测试就宣称完成
- 文档滞后于主线实现超过一个合并周期

### 4.3 两层 review 闸门

#### Layer 1：本地 review

检查：

- 边界是否越界
- 测试是否真实覆盖需求
- 是否引入文档/代码漂移
- 是否引入“伪完成”

#### Layer 2：PR review 留痕

检查：

- 是否符合四份核心事实源
- 合并后监控口径是否需要刷新
- Windows / Cloud 证据是否混写

**硬规则**：

- 未完成两层 review，不得 merge。

---

## 5. 状态刷新制度

### 5.1 何时必须刷新

以下任一情况发生，必须提交一次状态刷新：

1. 一条主线完成 2 到 3 个 PR
2. 测试精确绿基线改变
3. 主线完成度判断发生变化
4. 分母变化（如 inventory、coverage denominator）
5. 文档出现已知漂移

### 5.2 刷新内容

状态刷新最少要同步：

- `AGENTS.md`
- `CLAUDE.md`
- `docs/requirements.md`
- `docs/PROJECT-STRUCTURE.md`

必要时补：

- status doc
- dashboard
- baseline report

---

## 6. 双环境控制

### 6.1 Cloud 负责

- 跨平台实现
- `dotnet test`
- CI
- baseline 工件
- typed catalog / validator / runtime / migration / docs

### 6.2 Windows 负责

- `MetBench_Client` 编译
- WPF 运行
- UI 交互观察
- Windows-only 配置回执

### 6.3 双环境硬规则

- Cloud 通过 ≠ Windows 已验证
- Windows 回执旧于当前主线时，只能写“历史参考”，不能写“当前已验证”
- WPF/UI 需求若无 Windows 回执，不得标为完全闭环

---

## 7. 监控输出规范

正式监控输出必须按这个顺序：

1. **结论摘要**
2. **当前主线头**
3. **最近可审计精确绿基线**
4. **已完成 / 部分完成 / 未完成 / 待核实**
5. **风险点**
6. **下一步优先事项**

并且必须显式区分：

- 当前仓库状态
- 最近测试基线
- Windows 历史回执
- 历史计划 vs 当前活跃计划

## 8. 当前立即生效的执行裁决

截至 2026-05-25，本仓库立即采用以下裁决：

1. `origin/main` 是唯一主线真相层。
2. 当前仓库状态与完成度只认四份核心文档。
3. `MR 验证统一设计 v1.2` 已完成 PR-0..PR-10 + PR #110 review-fix。
4. v1.2 inventory 正式口径为 **44 MR + 4 Property**。
5. 当前最近可审计精确代码绿基线为 `e839214`：`1043 pass / 0 fail / 0 skip`。
6. 任何后续实现若触达 WPF/UI，都必须补新的 Windows 回执。

---

## 9. 不遵守本规则的后果

出现以下情况，视为流程失败，必须先纠偏再继续开发：

- 文档、监控、代码出现冲突
- 使用历史计划指导当前实现
- 以本地 worktree 状态冒充主线状态
- 以旧 Windows 回执冒充新主线验证
- 在设计未消歧前直接编程

本规则的目标不是增加流程，而是减少返工、误判和伪进度。
